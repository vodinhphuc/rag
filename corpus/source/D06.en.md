# Runbook: Agent reporting offline (SQ-1004)

Applies to SENTRIQ 4.2. The 3.8 procedure is retired.

## Symptoms

- Console shows the endpoint as **Offline**.
- Alert `SQ-1004` — no agent heartbeat for more than 15 minutes.
- The endpoint still responds to ping and the user is working normally.

## Establish scope before anything else

Open **Console → Fleet → Health** and read the offline endpoint count.

| Offline endpoints | Severity | Action |
|---|---|---|
| Under 5% | P3 | Continue with this runbook |
| 5% – 20% | P2 | Continue, and notify the Endpoint team |
| **Over 20%** | **P1** | **Escalate immediately.** This is a detection blind spot — do not self-serve |

Do this first. Many endpoints going offline together is usually not an agent
fault; it is infrastructure underneath them.

## Diagnosis

**1. Check the service on the endpoint**

```
sc query sq-agent          # Windows
systemctl status sq-agent  # Linux
```

If the service has stopped, read `C:\ProgramData\Sentriq\logs\agent.log` or
`/var/log/sentriq/agent.log` and find the last line before it stopped.

**2. Check connectivity to the collector**

The agent connects to the collector on port **8443** using mTLS.

```
Test-NetConnection sq-collector-01.internal.norvale.test -Port 8443
```

**3. Check the certificate**

If the log contains `SQ-1017`, the agent certificate has expired. Switch to
runbook **D07 — Certificate expiry**. Do not continue here.

**4. Check collector queue depth**

Open **Console → Infrastructure → Collectors** and read **Queue depth**.

If queue depth is above threshold the agents are being throttled, not genuinely
offline. That is `SQ-2011`, not `SQ-1004` — switch to runbook **D08**.

If queue depth is normal but the collector reports write failures, check event
store shard allocation. That is `SQ-6008` — switch to runbook **D09**.

## Resolution

Only after steps 3 and 4 have been ruled out.

```
sc stop sq-agent && sc start sq-agent          # Windows
systemctl restart sq-agent                     # Linux
```

The agent sends a heartbeat within **60 seconds** of restart. Re-check the
Console. If it is still offline after 5 minutes, escalate to the Endpoint team.

## Important

> **Do not restart sq-collector while handling SQ-1004.**
>
> The 3.8 procedure included a collector restart. That step was removed in 4.0.
> Restarting the collector forces every connected agent to re-handshake at once,
> which causes back-pressure (`SQ-2011`) and turns a single-endpoint incident into
> a fleet-wide one.

## When to escalate

- More than 20% of endpoints offline (P1).
- Agent still not sending heartbeats 5 minutes after restart.
- Agent log shows an error other than `SQ-1004` or `SQ-1017`.
