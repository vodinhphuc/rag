# Runbook: エージェントがオフライン表示になる (SQ-1004)

SENTRIQ 4.2 向け。3.8 の手順は廃止済み。

## 症状

- Console 上でエンドポイントが **Offline** と表示される。
- アラート `SQ-1004` — agent の heartbeat が 15 分以上途絶。
- エンドポイントは ping に応答し、利用者は通常どおり作業できている。

## 最初に影響範囲を確認する

**Console → Fleet → Health** でオフラインのエンドポイント数を確認する。

| オフライン率 | 重大度 | 対応 |
|---|---|---|
| 5% 未満 | P3 | 本 runbook を継続 |
| 5% – 20% | P2 | 本 runbook を継続し、Endpoint チームへ連絡 |
| **20% 超** | **P1** | **直ちにエスカレーション。** 検知不能状態であり、自己解決してはならない |

この手順を最初に行うこと。多数のエンドポイントが同時にオフラインになる場合、
原因は agent ではなく基盤側であることが多い。

## 切り分け

**1. エンドポイント上のサービス確認**

```
sc query sq-agent          # Windows
systemctl status sq-agent  # Linux
```

サービスが停止している場合は `C:\ProgramData\Sentriq\logs\agent.log` または
`/var/log/sentriq/agent.log` を確認し、停止直前の最終行を読む。

**2. collector への接続確認**

agent は port **8443** で mTLS により collector に接続する。

```
Test-NetConnection sq-collector-01.internal.norvale.test -Port 8443
```

**3. certificate の確認**

ログに `SQ-1017` がある場合、agent の certificate が期限切れ。runbook
**D07 — certificate 期限切れ対応** に移ること。ここで続行しない。

**4. collector の queue depth 確認**

**Console → Infrastructure → Collectors** で **Queue depth** を確認する。

queue depth が閾値を超えている場合、agent は throttle されているだけで実際に
オフラインではない。これは `SQ-1004` ではなく `SQ-2011` — runbook **D08** へ。

queue depth が正常でも collector が書き込みエラーを報告する場合は、event store
の shard 割り当てを確認する。これは `SQ-6008` — runbook **D09** へ。

## 対応

上記 3 と 4 を除外した後にのみ実施する。

```
sc stop sq-agent && sc start sq-agent          # Windows
systemctl restart sq-agent                     # Linux
```

再起動後 **60 秒** 以内に heartbeat が送信される。Console で再確認すること。
5 分経過しても Offline のままなら Endpoint チームへエスカレーション。

## 重要

> **SQ-1004 の対応中に sq-collector を再起動してはならない。**
>
> 3.8 の手順には collector 再起動が含まれていたが、4.0 で削除された。collector を
> 再起動すると接続中の全 agent が同時に再 handshake を行い、back-pressure
> (`SQ-2011`) を引き起こす。単一エンドポイントの障害が全体障害に拡大する。

## エスカレーション条件

- エンドポイントの 20% 超がオフライン (P1)。
- 再起動から 5 分経過しても heartbeat が届かない。
- agent ログに `SQ-1004` / `SQ-1017` 以外のエラーがある。
