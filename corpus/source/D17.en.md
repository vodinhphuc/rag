# Retention and storage planning

Applies to SENTRIQ 4.2. How the event store uses disk, how retention works, and
how to plan capacity. Rendered as a workbook.

## Retention model

The store keeps telemetry for a configurable window, 90 days by default. A nightly
retention job deletes data past the window. If the job cannot finish inside its
window it reports `SQ-6014` (retention job overrun) and the next night's job
starts behind.

## Capacity per component

| Data type | Source | Retained | Approx per 1000 endpoints/day |
|---|---|---|---|
| Process telemetry | agent | 90 days | 12 GB |
| Network telemetry | agent | 90 days | 8 GB |
| Detection events | sq-detect | 180 days | 0.5 GB |
| Policy/audit log | sq-policy | 365 days | 0.1 GB |
| Console access log | sq-console | 365 days | 0.05 GB |

Detection events and audit logs are kept longer than raw telemetry because they
are small and needed for investigations after the fact.

## Planning a fleet expansion

Before onboarding a large group, estimate the added daily volume from the table
and confirm the store has headroom for it across the full retention window, not
just one day. The most common capacity mistake is planning for one day of the new
load and being surprised 90 days later when it has all accumulated.

## When retention overruns

`SQ-6014` is a warning, not an outage — until it is. A job that overruns for
several nights lets disk fill, and a full store node causes shard unassignment
(`SQ-6008`, a P1). Do not ignore repeated `SQ-6014`.

```
sentriqctl store retention status
sentriqctl store retention run --force
```

Forcing a run clears the immediate backlog. If overruns recur, the window is too
long for the disk or the fleet has grown past the plan — expand disk or shorten
retention, do not just keep forcing.
